<Section aria-labelledby="checkmate-system-title">
  <TextBlock column="full">
    <p className="type-label text-muted">03. Shaping the experience</p>
    <h2 id="checkmate-system-title" className="type-title text-block__heading">A reading journey across three channels</h2>
    <p>I used the research to frame two design priorities: an <strong>accessible starting point</strong> and a <strong>manageable analysis view</strong>. I documented the flows and reusable components in Figma and Confluence, then carried those decisions into React.</p>
  </TextBlock>
  <Stack desktopSpaceBefore="none" gap="fluid" spaceBefore="fluid" width="wide" column="full">
    <Columns ratio="1:2" gap="6" align="center" minStart>
      <TextBlock measure="compact">
        <p className="type-label text-muted">Entry points</p>
        <h3 className="type-title text-block__heading">Start close to the article</h3>
        <p>The Chrome extension and Telegram bot gave readers ways to submit an article within their existing browsing and messaging habits. The website provided space for the detailed analysis.</p>
        <p>The bot returned a summary with a link to the full analysis. That made access to the link a critical part of the journey, particularly when a response became long.</p>
      </TextBlock>
      <Figure src="/images/work/checkmate/prototype-extensionoverlay.jpg" caption="Chrome extension as an alternative entry point into article analysis." aspect="16/9" alt="Chrome extension as an alternative entry point into article analysis." />

      <TextBlock measure="compact">
        <p className="type-label text-muted">Information hierarchy</p>
        <h3 className="type-title text-block__heading">Give each analysis room to be read</h3>
        <p>The output covered four categories: fact-checking, emotion, sentiment and propaganda techniques. I organised them into selectable tabs so readers could focus on one category at a time.</p>
        <p>The trade-off was that comparing categories required switching views. Prototype testing therefore needed to examine how people found a result and moved between tabs.</p>
      </TextBlock>
      <Figure
        src="/images/work/checkmate/designsystem-structure.jpg"

    <h2 id="checkmate-prototype-testing-title" className="type-title text-block__heading">Finding friction between the screens</h2>
    <p>We set up assigned taks on Maze to participants to examine navigation within the analysis and the handoff between Telegram and web platform.</p>

  <Stack desktopSpaceBefore="none" gap="fluid" spaceBefore="fluid" column="full">

      <div className="flow">
        <h3 className="type-title">a | Reaching the sentiment results</h3>
        <p>One task asked participants to open the Chrome extension, submit an article link and navigate to the <strong>Sentiment Analysis results tab</strong>.</p>
        <p>Maze reported <strong>96.2% success</strong> <em>but</em> a <strong>41.3% misclick rate</strong> for this task. The path report had included routes taken by the user through other analysis tabs before reaching the destination. As it did not take the 'usual' path that other users took to get to the sentiment tab directly, Maze reported it as a 'misclick' </p>
        <p> However, I decided that the paths alone could not establish whether the detours reflected exploration or confusion, so the success figure needed to be read alongside the navigation behaviour. Given the <strong>high success rate</strong>, we thus retained the tabs to allow movement between categories.</p>

  <TextBlock>
    <p className="type-label text-muted">06. Implementing the experience</p>
    <h2 id="checkmate-performance-title" className="type-title text-block__heading">Designing for the time between actions</h2>
    <p>Moving into implementation, we had to additionally factor that machine-learning analysis takes time, especially for longer articles.</p>
    <p>Together with the backend engineers, we worked on <strong>route-based lazy loading</strong> and <strong>client-side API response caching</strong>. These choices addressed page loading and revisiting results, ensuring that model inference time remained a separate constraint to be handled on its own.</p>
    <p>We did not measure the performance time before implementation, hence a metric comparison was not written for this segment.</p>
    <Stack desktopSpaceBefore="7" gap="2" spaceBefore="7">
      <p className="type-eyebrow">| design lesson</p>
      <p className="type-serif">Loading behaviour and repeated waits are part of the reading experience too.</p>

<Section aria-labelledby="checkmate-reflection-title">
  <TextBlock>
    <p className="type-label text-muted">08. Takeaways</p>
    <h2 id="checkmate-reflection-title" className="type-title text-block__heading">The design system continues in the code</h2>
    <p>Owning both the design reference and the React interface made consistency tangible. Component states, navigation, responsive layouts and loading behaviour all affected how the intended experience survived implementation.</p>
    <p>The Telegram issue reinforced the need to follow a journey beyond an individual screen: a readable summary still depended on an accessible link to the next step. Evaluating the revised mockup and then testing the implemented flow with the client addressed different stages of that journey.</p>
  </TextBlock>

  <TextBlock spaceBefore="8" desktopSpaceBefore="8">
    <h3 className="type-title">What I would validate next</h3>
    <p>I would test whether readers correctly understand uncertain model outputs, distinguish sentiment from factual accuracy and explain why a claim was flagged. That would connect the goal of approachable analysis with evidence of comprehension and better-informed judgement.</p>
    <p>I would also evaluate the waiting experience on slower connections and measure initial-load and repeat-visit performance to establish the user benefit of the implementation choices.</p>
    <Quote>
      <p><em>A consistent interface starts in Figma, but its behaviour is decided just as much in the browser.</em></p>
