<Statement label="The challenge">
  How could property search help people find the <strong>right place</strong> with an <strong>incomplete street name</strong>?
</Statement>

<section className="editorial-section editorial-section--overview" aria-labelledby="project-m-overview-title">

    <p className="editorial-eyebrow">01. Overview</p>
    <h2 id="project-m-overview-title" className="type-title">Making property search more forgiving</h2>
    <p>During my Accenture internship, I worked on search enhancements for a low-code real estate management system in the public sector. The work focused on helping people retrieve properties when the street name they entered was incomplete or truncated.</p>
    <p>My role connected stakeholder feedback, functional specifications and frontend implementation. I co-facilitated feedback sessions with agency track leads and a cross-functional team, defined partial-string search behaviour, and implemented client-side input debouncing.</p>
    <p>We broke the overall search improvement into separate design requirements that could be scoped across <strong>roughly three to four sprints</strong> during my summer internship.</p>
    <p>From a UX perspective, the work involved two connected questions: <strong>what should the search accept, and when should it respond?</strong></p>

<section className="editorial-section editorial-section--solutions" aria-labelledby="project-m-decisions-title">
  <div className="editorial-section__intro flow">
    <p className="editorial-eyebrow">03. Design decisions</p>
    <h2 id="project-m-decisions-title" className="type-title">Designing what happens between typing and finding</h2>
    <p>The changes addressed the behaviour behind the search field. One made the input more flexible; the other controlled the timing of requests.</p>
  </div>
  <div className="solution-list">
    <article className="solution">
      <div className="solution__copy flow">
        <p className="editorial-eyebrow">Decision 01 · Query handling</p>
        <h3 className="type-title">Let part of a street name be enough to start</h3>
        <p>I defined the functional specifications for retrieving properties from incomplete or truncated street names. The design intent was to reduce how much of the name a person needed to enter before the search could help them.</p>
        <p>The trade-off is <strong>flexibility versus specificity</strong>: a shorter string can correspond to more than one street. Retrieving a match therefore answers only part of the UX question; the person still needs to recognise the intended property.</p>
        <p>The scope described here is partial-string retrieval. Whether the broader results are easy to distinguish remains an important question for further usability validation.</p>
      </div>

    <article className="solution solution--reverse">
      <div className="solution__copy flow">
        <p className="editorial-eyebrow">Decision 02 · Interaction timing</p>
        <h3 className="type-title">Wait for a pause in typing</h3>
        <p>I implemented client-side input debouncing so search requests could wait for a pause in input. Further typing resets that wait, grouping closely spaced keystrokes into fewer requests.</p>
        <p>The trade-off is <strong>request volume versus response delay</strong>. A longer wait can suppress more intermediate requests, but can also make the interface feel slow. Sending a request for every keystroke responds sooner to each edit, while generating more endpoint activity.</p>
        <p>The aim was to avoid unnecessary intermediate requests while keeping the search responsive enough to support the task.</p>
      </div>

    <h2 id="project-m-outcomes-title" className="type-title">Fewer requests, with a more useful search</h2>

    <p>Responsiveness also improved. Without the original test protocol or timing measurements, I treat that as a qualitative outcome; the 30% figure refers specifically to request load.</p>

<section className="editorial-section editorial-section--outcome" aria-labelledby="project-m-reflection-title">
  <div className="editorial-section__intro editorial-section__intro--storyboards flow">
    <p className="editorial-eyebrow">06. Takeaways</p>
    <h2 id="project-m-reflection-title" className="type-title">Search quality includes the moments before a result</h2>
    <p>This work showed me how functional specifications and frontend behaviour shape the user experience. Supporting an incomplete street name reduces the information someone needs to supply; controlling request timing changes how the system responds while they enter it.</p>
    <p>Working across stakeholder feedback, specifications and implementation helped me connect a reported pain point to the behaviour behind the interface.</p>
  </div>
  <div className="editorial-section__intro editorial-section__intro--storyboards flow">
    <h3 className="type-title">What I would validate next</h3>
    <p>I would test the search with agency users using full, partial and ambiguous street names. I would observe whether they could recognise the intended property, how often they reformulated a query, and whether the pause before results felt responsive.</p>
    <p>I would also retain a repeatable before-and-after benchmark for request count and time to the first relevant result, using the same queries and typing sequences. That would help assess the debounce trade-off across different input patterns and separate endpoint efficiency from successful property selection.</p>
  </div>
