<Section aria-labelledby="project-m-decisions-title">
  <TextBlock column="full">
    <p className="type-label text-muted">03. Design decisions</p>
    <h2 id="project-m-decisions-title" className="type-title text-block__heading">Designing what happens between typing and finding</h2>
    <p>The changes addressed the behaviour behind the search field. One made the input more flexible; the other controlled the timing of requests.</p>
  </TextBlock>
  <Stack desktopSpaceBefore="none" gap="fluid" spaceBefore="fluid" width="wide" column="full">
    <Columns ratio="1:2" gap="6" align="center" minStart>
      <TextBlock measure="compact">
        <p className="type-label text-muted">Decision 01 · Query handling</p>
        <h3 className="type-title text-block__heading">Let part of a street name be enough to start</h3>
        <p>I defined the functional specifications for retrieving properties from incomplete or truncated street names. The design intent was to reduce how much of the name a person needed to enter before the search could help them.</p>
        <p>The trade-off is <strong>flexibility versus specificity</strong>: a shorter string can correspond to more than one street. Retrieving a match therefore answers only part of the UX question; the person still needs to recognise the intended property.</p>
        <p>The scope described here is partial-string retrieval. Whether the broader results are easy to distinguish remains an important question for further usability validation.</p>
      </TextBlock>

    <Columns ratio="2:1" gap="6" align="center" reverse minEnd>
      <TextBlock measure="compact">
        <p className="type-label text-muted">Decision 02 · Interaction timing</p>
        <h3 className="type-title text-block__heading">Wait for a pause in typing</h3>
        <p>I implemented client-side input debouncing so search requests could wait for a pause in input. Further typing resets that wait, grouping closely spaced keystrokes into fewer requests.</p>
        <p>The trade-off is <strong>request volume versus response delay</strong>. A longer wait can suppress more intermediate requests, but can also make the interface feel slow. Sending a request for every keystroke responds sooner to each edit, while generating more endpoint activity.</p>
        <p>The aim was to avoid unnecessary intermediate requests while keeping the search responsive enough to support the task.</p>

<Section aria-labelledby="project-m-reflection-title">
  <TextBlock>
    <p className="type-label text-muted">06. Takeaways</p>
    <h2 id="project-m-reflection-title" className="type-title text-block__heading">Search quality includes the moments before a result</h2>
    <p>This work showed me how functional specifications and frontend behaviour shape the user experience. Supporting an incomplete street name reduces the information someone needs to supply; controlling request timing changes how the system responds while they enter it.</p>
    <p>Working across stakeholder feedback, specifications and implementation helped me connect a reported pain point to the behaviour behind the interface.</p>
  </TextBlock>
  <TextBlock spaceBefore="8" desktopSpaceBefore="8">
    <h3 className="type-title">What I would validate next</h3>
    <p>I would test the search with agency users using full, partial and ambiguous street names. I would observe whether they could recognise the intended property, how often they reformulated a query, and whether the pause before results felt responsive.</p>
    <p>I would also retain a repeatable before-and-after benchmark for request count and time to the first relevant result, using the same queries and typing sequences. That would help assess the debounce trade-off across different input patterns and separate endpoint efficiency from successful property selection.</p>
